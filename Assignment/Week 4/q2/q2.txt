Q1 First-pass triage

(Host: x86-64, 8 logical CPUs, glibc/Linux. The `perf` PMU is fully unavailable here:
`kernel.perf_event_paranoid = 4` and the process lacks CAP_PERFMON / passwordless sudo, so
`perf_event_open` is denied outright and `perf stat`/`record` error out instead of returning
counters. The figures below therefore come from getrusage via `/usr/bin/time -v`, not from
hardware counters; IPC requires the PMU and so remains unmeasurable on this machine.)

1. IPC value from this machine: not available. Computing `insn per cycle` requires the hardware
`cycles` and `instructions` counters, which the PMU here will not expose (access denied, not
just `<not supported>`). What can be measured still shows the workload is heavily synchronization-
and scheduling-bound rather than payload-bound: throughput is only ~2.0 M ops/sec (e.g.
10,017,831 items consumed in 5.04 s) for 6 producers + 1 consumer on 8 cores, and the run logs
212,489 involuntary context switches in ~5 s — the signature of constant `sched_yield()` spinning
under contention, not of useful work being retired.

2. The `sys` time is disproportionately high for a user-space lock-free queue (measured x86-64 run
via `/usr/bin/time -v`: user = 11.97s, sys = 7.54s, 384% CPU over 5.07s wall). A "lock-free" queue
that issues no explicit syscalls should spend almost no time in the kernel; 7.54s of sys time means
frequent hidden kernel entries from contention-driven yielding (`std::this_thread::yield()` ->
`sched_yield`, visible as `sched_yield@plt` in the producer disassembly) and from glibc allocator
internals (`operator new`/`delete` per item) under heavy multithreaded pressure.

Q2 Locating the hot functions

1. Top symbols from `perf report` include kernel scheduler addresses, `__sched_yield`, and `producer_thread(...)`; allocator paths (`_int_malloc`, `_int_free_chunk`, `malloc`, `cfree`) are also significant. This indicates the implementation is spending many cycles in scheduling and heap management overhead, not just queue logic.

2. With `-O3`, enqueue/dequeue logic is inlined into caller code (for this binary, `producer_thread` carries the hotspots). So function-level `perf report` is not enough by itself; you need instruction/source-level inspection (`perf annotate`, or disassembly + source mapping) to identify the exact bottleneck instructions and lines.

Q3 Diagnosing bottlenecks

On this x86-64 host `perf annotate` could not run (PMU access denied, see Q1), so per-instruction
cycle percentages are not available here. The hot path is instead identified from the optimized
`producer_thread` disassembly (`objdump -d -C`), where `enqueue()` is fully inlined. The struct
layout is `head_` @ +0x00, `tail_` @ +0x08, `capacity_` @ +0x10, `storage_` @ +0x18 in `%r14`.
The critical-path instructions of the enqueue retry loop are:

- `29eb:  48 8b 36              mov    (%r14),%rsi`            ; load head_ (offset 0x00)
- `29ff:  f0 48 0f b1 0a        lock cmpxchg %rcx,(%rdx)`      ; CAS publish tail_ (offset 0x08)
- `2a04:  75 e2                 jne    29e8 <...+0x28>`        ; retry branch after the CAS
- `2a08:  49 f7 76 10           divq   0x10(%r14)`             ; current_tail % capacity_

These are the x86-64 forms the assignment expects (`mov`/`lock cmpxchg`/`jne`/`divq`); the ARM64
equivalents are `ldar`/`casal`/`b.ne`/`udiv`. (Also visible nearby: `call sched_yield@plt` on the
buffer-full path and `lock add %rbx, total_produced`, corroborating the Q1 sys-time story.)

1. The load `mov (%r14),%rsi` reads `head_`, which producer threads never write. It is expensive
because multiple cores repeatedly contend on the same cache line (producers read `head_` while the
consumer updates it), causing coherence traffic (MESI invalidation/ownership transitions) and extra
latency.

2. The branch after CAS (`jne` after `lock cmpxchg`, analogous to ARM `b.ne` after `casal`) is where
retries/spin become visible. The atomic CAS initiates the coherence transaction, but the
waiting/retry penalty materializes in control flow and pipeline recovery around the branch, so
sampled stalls (sample skid) typically accumulate on the branch rather than the `cmpxchg` itself.

3. The division hotspot (`divq`, ARM `udiv`) comes from modulo indexing in enqueue/dequeue:
`index = current_tail % capacity_` (and similarly `current_head % capacity_`). A 64-bit integer
divide on the critical path is expensive compared with bit-masking or simple arithmetic, so it
meaningfully throttles throughput. (Note `capacity_` is 65536, a power of two, so `& (capacity_-1)`
would be sufficient — the compiler cannot prove this at compile time because `capacity_` is a
runtime field, hence the real `divq`.)

Q4 Understanding the atomic memory ordering flaw

1. Default `seq_cst` on each atomic load/store/CAS enforces a single global order across threads. At hardware level this can force stronger fences/ordering constraints, reduce store-buffer freedom, and limit overlap/reordering, increasing pipeline stalls under contention.

2. Acquire-release is sufficient here:
- Acquire load: prevents later reads/writes from moving before the load; consumer that acquires an index sees data written before the matching release.
- Release store: prevents earlier writes from moving after the store; producer publishes fully initialized data before making it visible.
This pairing is enough so the consumer never observes a claimed slot before its payload is fully written.

Q5 Heap allocation and kernel overhead

1. `virtual ~LogEntry()` adds a hidden vptr (pointer-sized metadata) to every object. This increases object footprint and reduces effective cache density; sequential consumer scans touch more cache lines and suffer worse locality.

2. `new LogEntry()`/`delete` on the hot path route through glibc allocator internals, which under high thread contention use arena synchronization and can spin/block. That effectively serializes threads at allocator boundaries, which explains both allocator hotspots and elevated `sys` time despite an otherwise lock-free queue algorithm.

Q6 Proposing and justifying fixes

1. Atomic index layout flaw:
- Flaw: `head_` and `tail_` are adjacent and induce false sharing/coherence ping-pong.
- Fix: place them on separate cache lines (padding or `alignas(64)` wrappers).

2. Memory-ordering flaw:
- Flaw: all atomics default to `seq_cst`, stronger than necessary.
- Fix: use acquire/release (and relaxed where safe) for queue publication/consumption semantics.

3. Allocation/object-layout flaw:
- Flaw: per-item dynamic allocation plus virtual destructor in hot path creates allocator and cache overhead.
- Fix: store `LogEntry` inline in a preallocated ring and remove virtual dispatch metadata.

Q7 Expected perf-stat movement after fixes

1. page-faults: down (or roughly same low level). Fewer allocator calls reduce page churn/allocator metadata pressure.

2. instructions: down. Removing malloc/free traffic and retry-heavy slow path reduces total retired instructions for the same work.

3. IPC: up modestly (though may still remain low). Fewer stalls/fences/contention events improve instruction issue efficiency.

4. sys time: down significantly. Less yielding and less allocator/internal kernel interaction.

5. Throughput (M ops/sec): up significantly. The hot path becomes shorter and less contended.

Why IPC may still look low after fixes:
In contention-heavy concurrent workloads, throughput can improve even when IPC stays modest, because useful progress depends on synchronization/coherence latency and scheduling dynamics, not only instruction issue width. A low IPC here mainly indicates the cores still spend time waiting (memory/coherence/serialization), not that the algorithm is necessarily slow in terms of completed operations.

Commands run (x86-64 host):
- `make && ./ipc_bench`                          # baseline: ~2.0 M ops/sec
- `perf stat ./ipc_bench`                        # BLOCKED: perf_event_paranoid=4, no CAP_PERFMON -> "Access to performance monitoring ... is limited"
- `perf record -g ./ipc_bench`                   # BLOCKED: same PMU access error

- `objdump -d -C ipc_bench`                      # static disassembly of producer_thread (enqueue inlined) -> x86-64 hot instructions above

Environment limitation: `perf stat`/`record`/`report`/`annotate` cannot run on this VM because the
PMU is gated by `kernel.perf_event_paranoid = 4` and no elevated capability/sudo is available, so
IPC and per-instruction cycle percentages are unmeasurable here. The conceptual analysis is
unaffected, and the hot x86-64 instructions are confirmed by disassembly; on a host with
`perf_event_paranoid <= 2` (or CAP_PERFMON) re-running `perf stat`/`annotate` would fill in the IPC
figure and per-line percentages.
